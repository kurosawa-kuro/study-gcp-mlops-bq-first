# 02 移行ロードマップ — 不動産ハイブリッド検索への題材差し替え

本リポジトリの **決定的仕様**。`docs/README.md §2` の権威順位により、`01_仕様と設計.md` / `README.md` / `03_実装カタログ.md` / `CLAUDE.md` はすべて本書に従属する。

本書は、旧仕様 (カリフォルニア住宅価格回帰) を **不動産ハイブリッド検索 (Hybrid Search + Learning-to-Rank)** に差し替えるための決定事項を記す。設計思想は `/home/ubuntu/repos/study-gcp-mlops/study-llm-reranking-mlops` (以下 "参考実装") から流用し、ランタイム / IaC / CI-CD / 境界テストは本リポジトリ既存構造を継承する。

## §1. 題材の定義

### §1.1 ユースケース

ユーザが自由文クエリ (例: `"赤羽駅徒歩10分以内 ペット可 2LDK"`) + 絞り込みフィルタ (家賃上限・間取り・築年数) を入れると、**関連度順に並んだ物件リスト上位 20 件** を返す検索 API。内部的には次の 3 段構成:

```
[クエリ文 + フィルタ]
     │
     ▼
┌───────────────────────────────────────────┐
│ STEP 1 — 候補抽出 (Candidate Generation)  │
│   BigQuery VECTOR_SEARCH (cosine)         │
│   + WHERE 句によるフィルタ絞り込み        │
│   → 候補 100 件                           │
└───────────────────────────────────────────┘
     │
     ▼
┌───────────────────────────────────────────┐
│ STEP 2 — 意味スコア付け (Semantic)        │
│   クエリ埋め込み (ME5) と                 │
│   物件埋め込みのコサイン類似度            │
│   → me5_score を特徴量として付与          │
└───────────────────────────────────────────┘
     │
     ▼
┌───────────────────────────────────────────┐
│ STEP 3 — 再ランキング (LightGBM)          │
│   9 次元特徴量 → lambdarank predict       │
│   → 上位 20 件                            │
└───────────────────────────────────────────┘
     │
     ▼
[検索結果 + ranking_log に記録 → Pub/Sub]
```

### §1.2 入出力契約

| 面 | 形 |
|---|---|
| 入力 | `query: str` (日本語想定) / `filters: {max_rent, layout?, max_walk_min?, pet_ok?, max_age?}` / `top_k: int (default 20)` |
| 出力 | `List[{property_id, score, title, rent, layout, walk_min, age_years, city, ward, me5_score, lexical_rank}]` |
| 副作用 | `mlops.search_logs` に request、`mlops.ranking_log` に候補 100 件 × スコアの明細を publish |

### §1.3 スコープ外 (採用しない)

- 商品検索 / 社内規定検索 (旧 `01_仕様と設計.md` で言及されていたもの)
- 画像検索 / 地図タイル配信 / ルーティング
- パーソナライゼーション (user_id ごとの Context Features)。将来拡張として設計は残すが Phase 8 以降
- 画像埋め込み (物件写真) — テキストのみ

## §2. 参考実装からの流用と差し替え対照表

参考実装: `/home/ubuntu/repos/study-gcp-mlops/study-llm-reranking-mlops` (PostgreSQL + Meilisearch + Redis + Docker Compose ベース)。

| 参考実装での構成 | 本リポジトリでの再設計 | 流用度 |
|---|---|---|
| Meilisearch (lexical candidate retrieval) | **BigQuery VECTOR_SEARCH + フィルタ SQL** | **差し替え** (GCP-native 化) |
| `intfloat/multilingual-e5-large` (1024d) | `intfloat/multilingual-e5-base` (768d) | **ダウンサイズ** (Cloud Run memory / コールドスタート制約) |
| Redis キャッシュ (TTL 120s) | **不採用**。API 内で最新 `run_id` を lifespan 固定 + BQ 結果は `request_id` 単位 | 削除 |
| PostgreSQL (properties / search_logs / property_features) | **BigQuery** (同名テーブルを BQ へ移植、IaC 化) | 差し替え |
| FastAPI `/search` `/feedback` | **FastAPI `/search` `/feedback` + `/events/retrain` + `/jobs/check-retrain`** (既存エンドポイントを Phase 4-6 から継承) | 流用 |
| Docker Compose (api + postgres + meilisearch + redis) | Cloud Run Service + Cloud Run Jobs + BigQuery + Pub/Sub + Cloud Scheduler | 差し替え |
| LightGBM `lambdarank`、group = query | **同じ** (目的関数・group 化方式は維持) | **完全流用** |
| 特徴量 8 次元 (price / walk_min / age / area / ctr / fav_rate / inquiry_rate / me5_score) | **9 次元** (上記 + `lexical_rank` 追加。候補段の順位を feature 化) | 流用 + 1 列追加 |
| 評価: NDCG@10 / MAP / Recall@20 | **同じ** (指標・Gain 定義を踏襲) | 完全流用 |
| ラベル Gain: inquiry=3 / favorite=2 / click=1 / none=0 | **同じ** | 完全流用 |
| `training_dataset_builder.py` (5000 ログ取得) | BigQuery SQL (Scheduled Query で学習用テーブル生成) + `jobs/` で read | 書き換え (SQL 化) |
| 日次 `aggregate_daily_property_stats` | **Dataform scheduled execution** (`feature_mart.property_features_daily`) | 書き換え (Dataform 化) |
| `me5_embedding_service.py` | `common/src/common/embeddings/e5_encoder.py` + Cloud Run Jobs `embedding-job` | 書き換え (I/O 層分離) |

**原則**: 参考実装の「純粋ロジック」(ranking metrics / label gain / feature 計算式 / LambdaRank パラメタ) は可能な限りコピーしたまま流用する。参考実装の「I/O 層」(PostgreSQL / Meilisearch / Redis / Docker Compose) は本リポジトリの既存 Port/Adapter 構造に吸収する。

## §3. 採用 / 不採用 決定表

### §3.1 不採用 (明示的に除外)

| 技術 | 理由 |
|---|---|
| Vertex AI (Pipelines / Training / Endpoints / Model Registry / Feature Store / Experiments / Model Monitoring) | 既存方針を継承。LightGBM × Cloud Run で完結させる |
| **Vertex AI Text Embeddings API** (`text-multilingual-embedding-002`) | Vertex AI 全面不採用方針と整合。自前で ME5 を Cloud Run 上で動かす |
| **BQML `ML.GENERATE_EMBEDDING`** | 内部で Vertex AI remote model を呼ぶため不採用 |
| **BQML `CREATE MODEL`** (LambdaRank 非対応のため元から候補外) | Cloud Run Jobs + LightGBM lambdarank で代替 |
| Meilisearch / Elasticsearch / OpenSearch | GCP-native の BigQuery VECTOR_SEARCH を使う |
| Redis / Memorystore | API 層でのオンラインキャッシュは導入しない (初期)。必要になったら Phase 9 で検討 |
| PostgreSQL / Cloud SQL | すべて BigQuery に寄せる (bq-first 原則) |
| Faiss / ScaNN 自前ホスト | 候補抽出は BigQuery VECTOR_SEARCH に集約 |
| Cross-encoder reranker (BERT 系) | 推論レイテンシとコストが見合わない。LightGBM ランカで代替 |

### §3.2 採用

| 技術 | 用途 | 置き場 |
|---|---|---|
| **BigQuery VECTOR_SEARCH** (IVF index) | 候補抽出 (cosine 類似度 top-100) | `mlops-dev-a.feature_mart.property_embeddings` on 768d VECTOR 列 |
| **`intfloat/multilingual-e5-base`** (sentence-transformers) | クエリ / 物件テキストの埋め込み | Cloud Run Service でロード (query 側) + Cloud Run Jobs (物件 batch 側) |
| **LightGBM `lambdarank`** | 再ランカ | Cloud Run Service で predict、Cloud Run Jobs で train |
| **Dataform** | 日次特徴量集計 (CTR / 好意率 / 問い合わせ率) | `feature_mart.property_features_daily` |
| **Pub/Sub → BQ Subscription** | ranking_log / search_logs の streaming 取り込み | 既存パターンを流用 |
| **Cloud Scheduler + Eventarc** | 再学習判定・embedding 更新 | 既存 `check-retrain-daily` を拡張 |
| **W&B (Weights & Biases)** | 学習実験管理 | 既存継承。ranker メトリクス (NDCG@10 / MAP / Recall@20) を送信 |

## §7. ML モデル

### §7.1 埋め込みモデル

- `intfloat/multilingual-e5-base` (768d、約 1.1GB fp32 / 約 550MB fp16)
- 参考実装の `multilingual-e5-large` からダウングレードする理由: Cloud Run Service `--memory 4Gi` 以内に LightGBM Booster + sentence-transformers を収めたい
- プロンプト規約 (ME5 要件): 埋め込み対象テキストに **`"query: "` / `"passage: "` の prefix を付ける**
  - 物件側 (バッチ): `"passage: {title}。{description}"`
  - クエリ側 (オンライン): `"query: {query}"`
- GCS 配置: `gs://mlops-dev-a-models/encoders/multilingual-e5-base/{version}/`
- lifespan ロード時間: Cloud Run `--min-instances 1` 前提で約 8–12 秒を許容 (コールドスタート回避のため `--min-instances 0` に下げない)

### §7.2 再ランカ (LightGBM `lambdarank`)

```python
params = {
    "objective": "lambdarank",
    "metric": ["ndcg"],
    "ndcg_eval_at": [5, 10, 20],
    "lambdarank_truncation_level": 20,
    "learning_rate": 0.05,
    "num_leaves": 31,
    "min_data_in_leaf": 50,
    "feature_fraction": 0.9,
    "bagging_fraction": 0.8,
    "bagging_freq": 5,
    "verbose": -1,
}
num_boost_round = 200
early_stopping = 20
```

主指標 `NDCG@10`。参考実装のパラメタをほぼ踏襲。`num_iterations` は参考実装 80 → 本リポジトリ 200 に引き上げ (early stopping で実効値は決まる)。

### Phase 4 完了条件 (必達ゲート)

Phase 4 は **「候補検索だけで成立する最小検索 API」** を合格条件にし、LambdaRank 学習済みモデルへの依存を**持ち込まない**。以下をすべて満たして初めて Phase 5 以降に進む:

1. `/search` エンドポイントが Cloud Run Service `search-api` で 200 応答を返す (ローカル `make api-dev` + ステージング双方)
2. BigQuery VECTOR_SEARCH で候補 100 件が取得できる (クエリ埋め込みは ME5 encoder で lifespan ロード済のものを使用)
3. **rerank 無し** でも検索結果上位 20 件 (= `lexical_rank` 1..20) を返却できる — つまり booster 未ロードでも `/search` が機能する
4. `mlops.ranking_log` に候補 100 件分の行が Pub/Sub → BQ Subscription 経由で記録される (`final_rank = lexical_rank`、`score = NULL`、`me5_score` は計算済み)
5. `/feedback` で `mlops.feedback_events` への publish ができる (ログ生成の疎通確認、LambdaRank 学習はまだ不要)

この段階では **LightGBM Booster は lifespan にロードしない**。ranker が無い状態で `/search` が単独で立つこと、ranking_log が流れることをもって Phase 4 完了とする。LambdaRank 学習 (Phase 3b の training-job を本番データで回す) と rerank 組み込みは Phase 6 以降で段階導入する。

**この合格条件を設ける理由**: 学習用プロジェクトでは「候補検索 + 埋め込み + 学習 + rerank + 監視 + 再学習」を同時に組もうとして全部載せで詰まりがち。候補検索が独立して動くことを強制ゲートにすると、VECTOR_SEARCH / ME5 ロード / BQ Subscription / `ranking_log` スキーマの 4 面が先に安定し、残りのレイヤを段階的に積める。

**Phase 10 系は破壊的** なので必ず単独 PR + User 確認。Phase 1–9 は共存期間で、各フェーズ単位でレビュー・マージ可。Phase 9 のステージング疎通が PASS していない状態で Phase 10 に進まない。
