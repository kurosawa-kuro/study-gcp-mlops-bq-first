# GCP-ML デモシナリオ

**目的:** MLOps パイプライン全体と、GCP 技術がどうつながるかを、コードと運用コマンドで短く見せる  
**想定尺:** 5〜7 分  
**画面:** ターミナル + エディタ + 必要に応じて BigQuery テーブル確認

---

## デモ全体の流れ

1. `SearchRequest` を確認して API の入力を把握する
2. `ranking.py` を開いて `/search` の主処理を読む
3. `candidate_retriever.py` を開いて `BigQuery VECTOR_SEARCH` を確認する
4. `make ops-search` を実行して検索結果を見る
5. `make ops-ranking` で順位情報を見る
6. `training_runs` / `ranking_log` / `feedback_events` の位置付けに触れる
7. `make ops-check-retrain` で再学習導線を説明する
8. 各工程と GCP 技術の対応を締めで整理する

---

## Step 1: API 入力の確認

### 開くファイル
- `app/src/app/schemas/search.py`

### 見せる項目
- `query`
- `limit`
- `max_rent`
- `layout`
- `max_walk_min`
- `pet_ok`

### ナレーション要点

> この API は推論工程の入口です。  
> ここで受けた条件が、BigQuery 上の候補抽出と後段の rerank につながります。

---

## Step 2: `/search` 主処理の確認

### 開くファイル
- `app/src/app/services/ranking.py`

### 注目箇所
- `run_search`
- query embedding
- candidate retrieval
- `_score_candidates`
- ranking log publish

### ナレーション要点

> 主線はここです。  
> クエリ埋め込みを作り、BigQuery で候補を取り、必要なら booster で並べ替え、最後に ranking_log を publish します。  
> API の責務が、HTTP 受付だけでなく、推論工程全体のオーケストレーションだと分かります。

---

## Step 3: BigQuery VECTOR_SEARCH の確認

### 開くファイル
- `app/src/app/adapters/candidate_retriever.py`

### 見せる箇所
- `BigQueryCandidateRetriever`
- SQL の WHERE 条件
- `VECTOR_SEARCH`
- `me5_score`
- `lexical_rank`

### ナレーション要点

> 候補抽出は BigQuery が担当します。  
> ここでは、埋め込み近傍検索と属性フィルタを同時に扱っています。  
> この教材では、BigQuery が保存先ではなく、MLOps パイプラインの複数工程を支える点が重要です。

---

## Step 4: 検索を実行する

### 例コマンド

```bash
make ops-search
```

### 画面で見るポイント
- 応答が返ること
- `me5_score`
- `final_rank`
- `score`

### ナレーション要点

> ここでは、検索結果が実際に返ることを確認します。  
> booster が載っていれば score が入り、未配置なら lexical rank ベースで返る設計です。  
> どちらの場合でも API 自体は成立する、という段階設計が見どころです。

---

## Step 5: 順位情報の確認

### 例コマンド

```bash
make ops-ranking
```

### 画面で見るポイント
- `lexical_rank`
- `final_rank`
- `score`
- `me5_score`

### ナレーション要点

> ここでは、候補抽出時の順番と最終順位の違いに注目します。  
> `me5_score` は特徴量の一つであって、そのまま最終順位ではありません。  
> ML がどこで介入しているかを、この画面で説明します。

---

## Step 6: BigQuery に何が残るか

### 触れるテーブル
- `feature_mart.property_embeddings`
- `mlops.training_runs`
- `mlops.ranking_log`
- `mlops.feedback_events`

### ナレーション要点

> このシステムは、検索して終わりではありません。  
> 物件埋め込み、学習履歴、返却順位、ユーザー反応が残るので、推論と再学習の間がつながっています。  
> ここが MLOps パイプラインのループ部分です。

---

## Step 7: 再学習導線を確認する

### 例コマンド

```bash
make ops-check-retrain
```

### 画面で見るポイント
- `reasons`
- `published`
- 条件判定の結果

### ナレーション要点

> 再学習は毎回無条件で回すのではなく、条件判定を通します。  
> フィードバック増加、NDCG 悪化、一定期間未学習のいずれかで trigger されます。  
> ここで、運用まで含めて GCP サービスがつながっていることを示します。

---

## Step 8: 締め

### 伝えること
- Cloud Run は API と Job の両方に使っている
- BigQuery は保存、特徴量、候補抽出、ログを横断して使っている
- Pub/Sub, Scheduler, Eventarc が再学習ループをつないでいる

### クロージング例

> この教材では、MLOps パイプライン全体と、GCP 技術がどう工程分担しているかを見ました。  
> 実装を読むときは、API だけでなく、データ加工、ログ、再学習導線まで一緒に追うのがポイントです。
